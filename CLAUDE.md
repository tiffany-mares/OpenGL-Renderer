## Project

A C++20 threaded OpenGL renderer whose real subject is three systems problems: thread-affine graphics contexts, a lock-free input handoff, and precise frame pacing on general-purpose OSes. The rotating cube is the demo, not the point. Built in phases (0–8); see the project outline for the full phase plan. **Phases 0–6c are complete as of 2026-07-27.** Phase 0: CMake scaffold, GLFW 3.4 via FetchContent, vendored glad2 single-header loader (`extern/glad/gl.h`, taken from GLFW's `deps/`), 3.3 core context with `glfwSwapInterval(0)`, CI matrix on windows-latest + ubuntu-latest (build + ctest). Phase 1: cube in `src/main.cpp` — 8 vertices / 36 indices / one VAO-VBO-EBO, depth test on, raw GLSL strings; per-face colors come from `flat` varyings plus provoking-vertex index winding (6 of the 8 shared vertices each carry one face color — do not reorder `kIndices` casually). Phase 2: `src/mat4.h` is the project's only math library — hand-rolled, header-only, **column-major** (`m[col*4+row]`, upload with transpose=`GL_FALSE`), parameter names `zNear`/`zFar` because Windows headers define `near`/`far` as macros; tests in `tests/mat4_test.cpp` (dependency-free, includes a 16-element perspective reference check) run via `ctest` locally and in CI; the cube rotates on the wall clock (`glfwGetTime`) through a `uMvp` uniform. Phase 3: the render is threaded — `src/main.cpp` owns the window and events only (poll/publish at ~1 kHz, **never** touches GL or makes the context current); `src/renderer.cpp` (`render_thread_main`) owns the context and every GL object, and `GLAD_GL_IMPLEMENTATION` lives there; `src/input_state.h` is the mutex-guarded snapshot channel (three backends arrive in Phase 4). Framebuffer size travels inside the snapshot because GLFW size queries are main-thread-only. Shutdown order is load-bearing: signal `stop` → render thread deletes GL objects and detaches context → join → `glfwDestroyWindow` on main. The decoupled rates are the payoff: a frame-rate cap no longer sets input latency. Testing note: when driving the app from scripts, wait for the window to exist before sending WM_CLOSE — `Process.CloseMainWindow()` silently fails (returns false) during the first few hundred ms of startup, which looks exactly like a shutdown hang. Phase 4: three handoff backends behind the abstract `InputChannel` in `src/input_state.h` — `MutexChannel` (default), `BitmaskChannel` (`atomic<uint32_t>`, keys only: no room for `publish_ns`, which is why it isn't the final answer), `SeqlockChannel` (full payload; the reader's payload copy is a deliberate, documented C++ data race — see README). Selected at startup via `--input=mutex|bitmask|seqlock` (`make_input_channel`); framebuffer size moved out of the payload into the packed-atomic `FramebufferSize` side channel; arrow keys yaw/pitch the cube through whichever backend is live. The seqlock stress test in `tests/input_test.cpp` derives every payload field from one counter and asserts consistency under a concurrent writer. Phase 5: the frame pacer — `src/pacer.h` (pure logic: `WelfordEstimator`, `FrameSchedule` with absolute deadlines and counted/resynced misses; unit-tested in `tests/pacer_test.cpp`) and `src/pacer.cpp` (platform layer: QPC + `CreateWaitableTimerExW` high-resolution with pre-1803 `timeBeginPeriod(1)` fallback on Windows, `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME)` + EINTR retry on Linux, `mach_wait_until` on macOS; `tests/pacer_smoke.cpp` exercises the real sleep path in ctest with loose bounds). `FramePacer` lives on the render thread, constructed there, `wait()` after swap; sleep short by Welford `mean + 3σ` (clamped to period/2, 1.5 ms bootstrap before 16 samples) then spin; `--fps N` / `--fps=N` (1..1000, 0/absent = uncapped); on exit it prints `frames / avg fps / missed deadlines`. `pacer_now_ns()` is the project's monotonic timestamp source for Phase 6. Phase 6a: per-run CSV logging — `--log PATH` (requires `--fps`; both `--log=` and space forms) records per-frame `frame,frame_start_ns,frame_end_ns,frame_time_ns,sleep_requested_ns,sleep_actual_ns,input_latency_ns,missed` via the preallocated `FrameLog` (`src/frame_log.h`, drop-and-count when full, CSV written only on exit — never IO or reallocation inside a timed frame). `FramePacer::wait()` returns `WaitStats`; `frame_time_ns` is deadline-to-deadline from consecutive `WaitStats::deadline_ns`. `publish_ns` now comes from `pacer_now_ns()` (main.cpp) so `input_latency_ns = consume − publish` is a same-clock subtraction; the bitmask backend logs latency 0 (cannot carry the timestamp — the Phase 4 asymmetry made visible). Instrumented frames run `synthetic_workload` (`src/workload.h`, xorshift64, ~100 µs fixed CPU) so CSVs measure the pacer, not the GPU; tests in `tests/frame_log_test.cpp`. Phase 6b (complete 2026-07-27): the pacing-strategy benchmark — `--pace=sleep|timer|timer_spin|spin` (default `timer_spin`, requires `--fps`; parsed by `parse_pace_strategy` in `src/pacer.h`, strategy dispatch in `FramePacer::wait()`), `--bench-frames N` self-terminating bench mode (N must exceed the 500-frame warmup; prints a parseable `bench: frames=... warmup=... measured=... cpu_ns=... wall_ns=... cpu_pct=...` line measuring render-thread CPU from the warmup boundary to loop exit — `QueryThreadCycleTime` calibrated once against the pacer clock on Windows since GetThreadTimes is tick-sampled, `CLOCK_THREAD_CPUTIME_ID` on POSIX). `bench/run_matrix.py` runs the 13-cell matrix (4 strategies × 60/144/240 Hz + uncapped, 10,000 frames/cell) and invokes `bench/summarize.py`; both are stdlib-only. Summarized results are committed under `bench/results/` (see `2026-07-27-pacing-matrix.md` for provenance and machine notes); raw per-frame CSVs under `bench/results/raw/` are git-ignored. Benchmark runs need AC power and an idle machine — on battery the Intel Arc driver frame-limits GL in SwapBuffers and the numbers are garbage. Phase 6c (complete 2026-07-27): the input-handoff benchmark — `InputChannel::read_retries()` (reader retry-loop iterations, relaxed diagnostic counter; nonzero only for seqlock), `--poll-hz N` (1..10000, default 1000; the main-thread poll loop is paced by its own `FramePacer` with TimerSpin — note this makes app benchmark cells run TWO concurrent busy-spinners, which depresses achieved poll rates: ~968–971 Hz at the 1 kHz target, ~3.1–3.4 kHz at 10 kHz; always interpret latency against the achieved rate), and every run exits with a parseable `handoff: backend=<name> poll_hz=<u> publishes=<u> wall_ns=<u> achieved_hz=<f.1> missed=<u> retries=<u>` line. `handoff_bench` (bench/handoff_bench.cpp) measures uncontended batched per-op costs (1 M iters × 5 reps — amortized throughput, not single-call latency) and a contended sweep (tight-loop reader vs paced publisher at 1 k/10 k/100 k/1 M/unthrottled publishes/s); ctest runs it as `handoff_bench_smoke` via `--quick`, plus `cube_rejects_poll_hz_zero`/`_high` verify `--poll-hz=0` and `=10001` exit 1 with `bad --poll-hz value`. `bench/run_handoff.py` runs the full ~10-minute protocol (micro-bench + 6 app cells) and invokes `bench/summarize_handoff.py` (both stdlib-only, deliberately standalone from the 6b scripts). Committed results: `bench/results/2026-07-27-handoff.md` (provenance, machine notes, three tables, measured crossover ≈100 k publishes/s) + `2026-07-27-handoff-summary.csv`. Phases 7+ (plots, further phases) do not exist yet — update this file as they land.

**Stack:** C++20, raw OpenGL 3.3 core profile, GLFW (windowing/events only), GLAD (GL loading), CMake with FetchContent for dependencies. Deliberately excluded: SDL, SFML, glm, any engine. Matrix math is hand-rolled (`mat4`, column-major to match OpenGL).

## Build

```
cmake -B build
cmake --build build --config Release
build/Release/cube.exe [--input=mutex|bitmask|seqlock] [--fps N] [--poll-hz N] [--log PATH]   # (Windows; build/cube on Linux)
ctest --test-dir build -C Release --output-on-failure   # all unit + smoke tests
```

On this machine `cmake` is at `C:\Program Files\CMake\bin\cmake.exe` (may not be in older shells' PATH); the generator is Visual Studio 16 2019 (MSVC 19.29).

Primary dev platform is Windows (MSVC); the project must also build on Linux, which is what keeps the platform timer abstraction honest. A separate Emscripten build (Phase 8) targets a single-threaded browser demo.

## Architecture constraints (non-negotiable, from the design)

- **Thread split:** the main thread creates the window and runs `glfwPollEvents` / input polling (GLFW requires this on the main thread) and never makes the GL context current. A render thread calls `glfwMakeContextCurrent`, loads GLAD, owns all GL objects, draws, and swaps. Shutdown order: signal render thread → it destroys GL objects → join → `glfwDestroyWindow` on main.
- **Input handoff:** three interchangeable backends behind one interface — `std::mutex` baseline, `std::atomic<uint32_t>` key bitmask, and a seqlock for the larger payload (keys + mouse delta + `publish_ns` timestamp). Selectable by command-line flag; mutex is the default. The seqlock's payload read is a known, deliberate C++ data race — documented, not hidden.
- **Frame pacer:** sleeps to an **absolute** deadline (`next += period`, never `now + period`), using per-platform high-res timers (`CreateWaitableTimerExW` high-resolution on Windows, `clock_nanosleep(CLOCK_MONOTONIC)` on Linux, `mach_wait_until` on macOS). Sleeps short of the deadline by a margin estimated online (Welford mean/variance), then spins. Missed deadlines are counted and resynced, never chased with short frames.
- **Instrumentation:** per-run CSV with per-frame timing fields; buffer is preallocated and flushed only on exit — never do file IO inside a timed frame. `frame_time_ns` is deadline-to-deadline; `input_latency_ns` = consume time − payload `publish_ns`.
- **`glfwSwapInterval(0)`** is set immediately at context creation — the pacer owns the frame clock, not vsync.
- **Emscripten build** is single-threaded and paced by `emscripten_set_main_loop` (gated with `#ifdef __EMSCRIPTEN__`); shaders there need `#version 300 es` and explicit precision qualifiers. Do not attempt threaded WebGL through GLFW — Emscripten's offscreen-canvas paths don't support it.

## Benchmarks

Phase 6 defines the benchmark protocol: 10,000 frames per configuration, first 500 discarded as warmup; pacing strategies × {60, 144, 240} Hz reporting p50/p95/p99/max/stddev/missed/CPU%; handoff backends at 1 kHz and 10 kHz publish rates. Thread CPU time via `QueryThreadCycleTime` (calibrated against `pacer_now_ns`; Windows) / `CLOCK_THREAD_CPUTIME_ID` (POSIX). Plots are generated by a Python script committed to the repo; result CSVs are committed from CI runs, not hand-copied.
